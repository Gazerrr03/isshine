# isshine 第 0 阶段：Init

建立项目的全局规格层（`spec/`），为每个工作流阶段定义处理策略，并建立检查点（项目切换上下文）。这是每个项目通常只执行一次的设置。

默认使用中文与用户对话，并生成中文 spec 内容；命令、文件名、状态字段、代码标识符保持原样。

## 前置条件

- 当前位于 git 仓库根目录
- 不存在 `spec/` 目录，或用户想重新配置

## 步骤

### 0. 进入 Plan Mode

**立即进入 Plan Mode。** Init 是设计对话，模型需要思考空间来帮助用户明确项目哲学、约束和处理偏好。本阶段输出会影响之后每一次 `/isshine` 调用。

### 1. 模板选择

开启对话来理解项目。采用 Vibe Generator 的思路：

- 这个项目为什么必须存在？
- 它服务谁？
- 它应该带来什么变化？
- 它绝不能变成什么？
- 人类与 AI 的协作模式是什么？

基于对话，推荐要启用的全局模板：

| 模板 | 推荐条件 |
|------|----------|
| `philosophy.md` | **始终推荐**：核心原则驱动所有决策 |
| `tech-constraints.md` | **始终推荐**：技术栈边界会影响每个 Issue |
| `anti-goals.md` | **始终推荐**：定义绝不能发生的事 |
| `design-system.md` | UI 较重的项目，或设计一致性很重要 |
| `glossary.md` | 多团队项目，或有领域专有术语 |
| `architecture.md` | 多模块项目，或模块边界很强 |

使用 `AskUserQuestion` 确认模板选择，可多选。至少启用 `philosophy.md`、`tech-constraints.md` 和 `anti-goals.md`。

### 2. 填写模板内容

对每个启用的模板：

1. 从 isshine 安装目录读取 `assets/templates/spec/<template>.md`
2. 以对话方式逐节向用户确认内容
3. 根据用户回答填写内容
4. **不要编造。** 证据不足时标记为 `[TODO: needs clarification]`
5. 写入 `spec/<template>.md`

创建的结构：

```text
spec/
├── philosophy.md
├── tech-constraints.md
├── anti-goals.md
└── [additional templates as selected]
```

### 3. 定义处理策略

**这是最关键的步骤。** 处理策略定义模型在后续每个阶段如何行动。它们不是硬编码规则，而是在本次对话中由用户和模型协商出来的约定。

逐个阶段讨论并记录：

```text
Phase: define
  └─ Plan Mode required: [yes/no]
  └─ Code exploration depth: [surface-level / 2-layer dependencies / full trace]
  └─ On incomplete spec/: [pause and flag / fill with TODO / ask user]
  └─ User review required: [yes — blocking / no — auto-proceed]

Phase: design
  └─ Plan Mode required: [yes/no]
  └─ Minimum risks identified: [2 / 3 / 5]
  └─ On insufficient design.md: [fallback to define / proceed with warnings]
  └─ User review required: [yes / no]

Phase: issue
  └─ Plan Mode required: [yes/no]
  └─ On completeness check failure: [block publish / publish with warnings]
  └─ Transcript extraction filter: [directional-only / all user inputs]
  └─ User review required: [yes / no]

Phase: pr
  └─ Plan Mode required: [yes/no]
  └─ On missing design.md: [degrade to diff summary / error]
  └─ Include verification checklist: [always / when tasks exist]
```

将达成一致的策略写入 `spec/.processing-strategies.md`。

### 4. 创建检查点上下文（Project Switch）

检查点是一个对话级信号，告诉模型“你现在服务的是这个项目”。

在 `spec/.project-context.md` 生成会话级上下文文件：

```markdown
# Project Context (auto-generated by isshine-init)

## Project Identity
- Name: [project name]
- Repository: [gh repo]
- Init Date: [date]

## Active Specs
- spec/philosophy.md — 核心原则
- spec/tech-constraints.md — 技术边界
- spec/anti-goals.md — 禁止模式
- [...]

## Processing Strategy Summary
[来自步骤 3 的简明摘要]

## Checkpoint
This file is loaded at the start of every /isshine conversation.
The model reads this to understand "what project it is serving."
```

### 5. 初始化路由

创建 `src/index.yaml`：

```yaml
project: [project-name]
created: [date]
routes:
  spec:
    - path: spec/philosophy.md
      type: global
      activated: true
    - path: spec/tech-constraints.md
      type: global
      activated: true
    - path: spec/anti-goals.md
      type: global
      activated: true
  features: []
```

### 6. 用户确认（阻塞点）

使用 `AskUserQuestion` 展示完整 init 输出：

- 已选择模板及其内容摘要
- 每个阶段的处理策略
- 项目检查点上下文

选项：

- "Confirm, init complete" — 完成 init，准备使用 `/isshine`
- "Adjust templates" — 回到模板内容
- "Adjust strategies" — 回到处理策略

## 退出条件

- `spec/` 目录存在，且内容已由用户确认
- `spec/.processing-strategies.md` 存在
- `spec/.project-context.md` 存在
- `src/index.yaml` 存在且路由正确
- 所有启用模板通过完整性检查（内容非空、非占位）

## Init 完成后

建议用户尝试第一个 `/isshine` 命令：

```text
✅ Init complete. Your project is ready.

Quick start:
  /isshine "add search functionality"

The model will:
  1. Load spec/ context + processing strategies
  2. Enter Plan Mode for requirement definition
  3. Generate proposal → design → tasks
  4. Deep-design risks and technical approach
  5. Synthesize a dual-layer GitHub Issue
```

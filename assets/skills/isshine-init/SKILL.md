# isshine Phase 0: Init

Set up the project's global specification layer (`spec/`), define processing strategies for each workflow phase, and establish the checkpoint (project switch context). This is a **one-time** per-project setup.

## Prerequisites

- Working in a git repository root
- No existing `spec/` directory (or user wants to reconfigure)

## Steps

### 0. Enter Plan Mode

**Immediately enter Plan Mode.** Init is a design conversation — the model needs thought space to help the user articulate philosophy, constraints, and processing preferences. The output of this phase shapes every subsequent `/isshine` invocation.

### 1. Template Selection

Start a dialogue to understand the project. Use the Vibe Generator's approach:
- Why must this project exist?
- Who is it for?
- What change should it produce?
- What must it never become?
- What is the human/AI collaboration model?

Based on the dialogue, recommend which global templates to activate:

| Template | Recommended When |
|----------|-----------------|
| `philosophy.md` | **Always recommended** — core principles drive all decisions |
| `tech-constraints.md` | **Always recommended** — tech stack boundaries affect every issue |
| `anti-goals.md` | **Always recommended** — what must never happen |
| `design-system.md` | UI-heavy project, or design consistency matters |
| `glossary.md` | Multi-team project, or domain-specific terminology |
| `architecture.md` | Multi-module project, or strong module boundaries |

Use `AskUserQuestion` to confirm template selection. Multiple choices allowed. At minimum, activate `philosophy.md`, `tech-constraints.md`, and `anti-goals.md`.

### 2. Fill Template Content

For each activated template:
1. Read the template from `assets/templates/spec/<template>.md` (these are in the isshine installation)
2. Present each section to the user conversationally
3. Fill in content based on user's responses
4. **Do NOT fabricate.** Thin evidence is marked as `[TODO: needs clarification]`
5. Write to `spec/<template>.md`

Structure created:
```
spec/
├── philosophy.md
├── tech-constraints.md
├── anti-goals.md
└── [additional templates as selected]
```

### 3. Define Processing Strategies

**This is the most critical step.** Processing strategies define how the model behaves in each subsequent phase. They are NOT hardcoded rules — they are **conventions negotiated between user and model** during this conversation.

For each phase, discuss and record:

```
Phase: define
  └─ Plan Mode required: [yes/no]
  └─ Code exploration depth: [surface-level / 2-layer dependencies / full trace]
  └─ On incomplete spec/: [pause and flag / fill with TODO / ask user]
  └─ User review required: [yes — blocking / no — auto-proceed]

Phase: design
  └─ Plan Mode required: [yes/no]
  └─ Minimum risks identified: [2 / 3 / 5]
  └─ On insufficient design.md: [fallback to define / proceed with warnings]
  └─ User review required: [yes / no]

Phase: issue
  └─ Plan Mode required: [yes/no]
  └─ On completeness check failure: [block publish / publish with warnings]
  └─ Transcript extraction filter: [directional-only / all user inputs]
  └─ User review required: [yes / no]

Phase: pr
  └─ Plan Mode required: [yes/no]
  └─ On missing design.md: [degrade to diff summary / error]
  └─ Include verification checklist: [always / when tasks exist]
```

Write the agreed strategies to `spec/.processing-strategies.md`.

### 4. Create Checkpoint Context (Project Switch)

The checkpoint is a **conversation-level signal** that tells the model "you are now serving this project."

Generate a session-level context file at `spec/.project-context.md`:

```markdown
# Project Context (auto-generated by isshine-init)

## Project Identity
- Name: [project name]
- Repository: [gh repo]
- Init Date: [date]

## Active Specs
- spec/philosophy.md — core principles
- spec/tech-constraints.md — tech boundaries
- spec/anti-goals.md — forbidden patterns
- [...]

## Processing Strategy Summary
[Concise summary from step 3]

## Checkpoint
This file is loaded at the start of every /isshine conversation.
The model reads this to understand "what project it is serving."
```

### 5. Initialize Router

Create `src/index.yaml`:

```yaml
project: [project-name]
created: [date]
routes:
  spec:
    - path: spec/philosophy.md
      type: global
      activated: true
    - path: spec/tech-constraints.md
      type: global
      activated: true
    - path: spec/anti-goals.md
      type: global
      activated: true
  features: []
```

### 6. User Confirmation (Blocking Point)

Use `AskUserQuestion` to present the complete init output:
- Selected templates and their content summary
- Processing strategies for each phase
- Project checkpoint context

Options:
- "Confirm, init complete" — finish init, ready to use /isshine
- "Adjust templates" — revisit template content
- "Adjust strategies" — revisit processing strategies

## Exit Conditions

- `spec/` directory exists with user-confirmed content
- `spec/.processing-strategies.md` exists
- `spec/.project-context.md` exists
- `src/index.yaml` exists with correct routes
- All activated templates pass completeness check (content is non-empty, non-placeholder)

## After Init

Suggest the user try their first `/isshine` command:

```
✅ Init complete. Your project is ready.

Quick start:
  /isshine "add search functionality"

The model will:
  1. Load spec/ context + processing strategies
  2. Enter Plan Mode for requirement definition
  3. Generate proposal → design → tasks
  4. Deep-design risks and technical approach
  5. Synthesize a dual-layer GitHub Issue
```
